## 📌 서비스 소개

우리는 종종 이런 순간을 놓치곤 합니다.

- 꼭 챙기고 싶었던 친구의 생일, 가족의 기념일, 약속했던 날  
- 말하고 싶었지만 바빠서, 어색해서, 타이밍을 놓쳐서 끝내 전하지 못한 말  
- “그때는 말하고 싶었는데…” 하고 마음에만 남은 말들  

이 말들은 사라진 게 아니라,  
언젠가 꼭 전하고 싶었던 마음으로 남아 있습니다.

**Dearly**는 이런 마음들을 **D-Day**라는 시간의 축 위에 예쁘게 기록하고,  
누군가와 함께 나누고, 때로는 나 자신에게도 남길 수 있는 공간입니다.

> 빠르게 흘러가는 채팅이 아니라,  
> _오래 남는 기록과 감정_ 을 만들기 위해 Dearly를 만들었습니다.

---

## 💌 Dearly는요..! 

Dearly는 조금 느리지만 의미 있는 소통 방식을 제안합니다.

- D-Day 중심으로 **마음이 남는 기록 생성**
- 폰트, 종이, 색상, 사진, 썸네일까지 직접 꾸미는 편지 형태의 기록
- 사라지지 않고, 나만의 타임라인에 오래 남는 감정 아카이브

---

## 💡 핵심 기능

### 1️⃣ D-Day 편지방 (그룹 편지)

하나의 D-Day를 기준으로 여러 명이 함께 편지를 쓰는 그룹 편지방 기능입니다.

- 친구, 가족, 팀원 등 여러 사람이 각자의 메시지를 하나의 편지방에 기록  
- 특정 날을 함께 기억하는 **디지털 추억 상자**
- 활용 예시  
  - 생일/기념일 롤링페이퍼  
  - 여행/프로젝트 회고  
- 편지방마다 이미지/텍스트/스타일을 커스텀해 **추억 앨범처럼 꾸미기 가능**

> Backend에서는 편지방, 참여자, D-Day, 편지 콘텐츠 중심의  
> 그룹 편지 생성/조회/관리 API를 제공합니다.

---

### 2️⃣ 1:1 편지쓰기 & 나에게 쓰는 편지

단순한 텍스트 메시지가 아닌, **직접 꾸미는 1:1 편지 기능**입니다.

- 폰트, 컬러, 종이 질감, 사진, D-Day 날짜까지 자유롭게 설정  
- 누군가에게 보내는 편지뿐 아니라  
  **나 자신에게 쓰는 편지**도 가능  
  - 목표, 다짐  
  - 위로, 회고  
  - 미래의 나에게

> Backend에서는 1:1 편지 생성/수정/삭제/조회 및  
> 발신자·수신자·D-Day 기준 필터링 기능을 제공합니다.

---

### 3️⃣ 수신함 – 감정 기록 아카이브

지금까지 주고받은 편지들이 정리되는 개인 수신함입니다.

- 사라지지 않고, 언제든 다시 꺼내볼 수 있는 감정/추억 아카이브  
- “그때 이런 이야기를 주고 받았었지”를 떠올릴 수 있는 공간

> Backend에서는 로그인한 사용자의  
> 보낸 편지 / 받은 편지 조회 API를 제공합니다.

---

### 4️⃣ 마이페이지, 공지센터, 알림

마이페이지에서는 Dearly의 전체 흐름을 한 눈에 볼 수 있습니다.

- **공지센터**  
  - 새로운 테마, 스타일 업데이트 소식  
  - 서비스 기능 추가/변경 공지  
- **알림**  
  - 친구 신청 / 편지 도착 / 편지 열람 가능 등  
  - 읽음/안읽음 상태 관리  

또한 사용자의 생일 정보를 기반으로:

> Backend에서는 공지, 알림, D-Day 계산 로직을 제공합니다.

## 🏗️ 기술 스택 (Backend)

- **Framework**: Django, Django REST Framework  
- **Auth**: JWT 인증 (djangorestframework-simplejwt)  
- **API 문서화**: drf-spectacular (Swagger / Redoc)  
- **기타**  
  - `.env` 환경 변수 기반 설정  
  - CORS 설정을 통한 FE/BE 분리 개발  
  - GitHub Flow 기반 협업  

---

## 📂 주요 도메인 / API 모듈

- `users/` – 회원가입, 로그인, 프로필, 마이페이지  
- `letterrooms/` – D-Day 그룹 편지방  
- `letters/` – 1:1 편지, 자기 자신에게 쓰는 편지  
- `notifications/` – 알림(편지 도착, 친구, 편지방 등)  
- `notices/` – 공지사항(테마 업데이트, 서비스 공지)

**🌿 Git 브랜치 전략**

본 프로젝트는 **GitHub Flow**를 기반으로 하되, 협업에 맞게 브랜치 전략을 다음과 같이 정의합니다:

- **main**: 배포용 브랜치 (항상 안정적인 버전 유지)  
- **dev**: 개발 통합 브랜치 (기능 개발 완료 후 PR 병합 대상)  
- **feat-기능명**: 개별 기능 개발 브랜치  
  - 예: `feat-login`, `feat-letterroom`, `feat-notification`

**💡 Workflow**

1. 기능 선택  
2. 브랜치 생성: `feat-기능명`  
3. 기능 개발 후 `dev` 브랜치로 Pull Request 생성  
4. 본인 제외 다른 팀원이 머지  
5. `main` 브랜치는 일정 단위로 `dev`에서 안정화된 버전만 머지
